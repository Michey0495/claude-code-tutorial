# Boris Cherny 氏の Claude Code TIPS（Claude Code チーム由来）

Claude Code を作った本人、Boris Cherny 氏が「Claude Code チームから直接集めた TIPS」を X で公開した。本人は「チームの使い方は自分とは全然違う。唯一の正解なんてない」と前置きしている。

ここでは、Boris 本人の元スレッド（13 TIPS）とチーム版 TIPS を統合した **22 個**を一覧でまとめる。

---

## セッション運用編

| # | TIPS | 内容 |
|---|------|------|
| 1 | ターミナルで 5 セッション並列実行 | タブに 1〜5 の番号を振り、システム通知で入力待ちを把握する。1 つが処理中の間に別タブで次の指示。シングルスレッドで待つのはもったいない。 |
| 2 | Web/モバイルでさらに 5〜10 セッション追加 | claude.ai/code 上でもセッションを並列で走らせている。朝はスマホからセッションを数個立ち上げることも。ただし 10〜20% は想定外で放棄される。 |
| 3 | セッションごとに独立した git checkout を使う | ブランチや worktree ではなく、セッションごとに独自の checkout を用意する。これで複数セッションが同時に同じファイルを触っても衝突しない。 |
| 4 | & コマンドでローカル→Web へセッション引き継ぎ | ローカルのセッションを & で Web 版に引き渡し、--teleport で戻すことも可能。デスクとモバイルの行き来に便利。 |

---

## モデル・設定編

| # | TIPS | 内容 |
|---|------|------|
| 5 | Opus 4.5 + thinking を全てのコーディングに使う | Sonnet より大きくて遅いが、ステアリングが少なく済みツール使用も上手い。結果的に Sonnet より速く終わることが多い。「スマートなモデルへの先行投資が後の修正コストを削減する」。 |
| 6 | CLAUDE.md をチームで git 管理する | 各チームがリポジトリに CLAUDE.md をチェックイン。Claude がやらかしたミスをその都度追記して改善サイクルを回す。現在のサイズは約 2.5k トークン。 |
| 7 | PR レビュー時に @.claude で CLAUDE.md を更新 | コードレビュー中に同僚の PR に @.claude タグを付けて、学びを CLAUDE.md に反映させる。GitHub Action と連携。 |

## ワークフロー編

| # | TIPS | 内容 |
|---|------|------|
| 8 | Plan Mode を最初に使う（Shift+Tab 2 回） | いきなりコードを書かせない。まず Plan Mode で計画を反復し、納得したら auto-accept edits モードに切り替えて一発実装。良い計画が一番大事。 |
| 9 | スラッシュコマンドで繰り返し作業を自動化 | .claude/commands/ に git でチェックインして共有。/commit-push-pr は 1 日に何十回も使う。インライン bash で git status 等のコンテキストを事前計算。 |
| 10 | サブエージェントで定型ワークフローを自動化 | code-simplifier（コード簡素化）、verify-app（E2E テスト）、build-validator（ビルド検証）など。「よくある PR の大半のワークフローを自動化するもの」として活用。 |
| 11 | PostToolUse フックでコードフォーマットを自動修正 | Claude のコードは「だいたい」整形されているが、最後の 10% にムラがある。PostToolUse フックで `bun run format || true` を実行し、CI 失敗を未然に防止。 |
| 12 | /permissions で権限を安全に管理する | --dangerously-skip-permissions はほぼ使わない。/permissions で `bun run build:*` や `bun run test:*` など安全なコマンドだけ事前許可する。設定はチーム資産として共有。 |

## 品質・検証編

| # | TIPS | 内容 |
|---|------|------|
| 15 | 検証ループが最重要（品質 2〜3 倍） | 「Claude に検証手段を与えること」が全 TIPS の中で一番大事。bash コマンド実行、テストスイート、ブラウザテスト、シミュレータなど。フィードバックループがあると成果物の品質が 2〜3 倍になる。 |
| 16 | 長時間タスクは検証付きで放置する | バックグラウンドエージェント、Stop フック、プラグインを組み合わせて、完了時に自動検証させる。長時間タスクに限り、サンドボックス内で --dangerously-skip-permissions を使うこともある。 |

## まとめ

Boris 氏の TIPS の本質は「プロンプトを工夫する」レベルではなく、**開発ワークフロー全体を Claude Code 前提で再設計すること**。並列化、Plan Mode、検証ループ、CLAUDE.md、スラッシュコマンド。この 5 つの柱で仕組みを作れば、1 人でも小さなエンジニアリングチーム並のアウトプットが出せる。
